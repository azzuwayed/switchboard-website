First-time install

Switchboard is still an unsigned beta, so the first launch can be blocked by macOS Gatekeeper. On newer macOS releases you may see "Switchboard.app is damaged and can't be opened. You should move it to the Trash.". On other systems you may see "cannot be opened because Apple cannot check it for malicious software" dialog. Apple Developer ID signing and notarization land later — until then the one-liner below clears it. You only do this once per machine; future OTA updates inherit the trust. There are two ways to do it below — either one works on its own, so start with the recommended one.

  1. The one-line fix Recommended

    After dragging Switchboard.app into /Applications, open Terminal and run:

    xattr -dr com.apple.quarantine /Applications/Switchboard.app

    This removes the quarantine attribute Safari added to the download. Launch Switchboard normally afterwards. Works on every supported macOS version.

  2. Open Anyway when offered

    After the first blocked launch, open System Settings → Privacy & Security, scroll to Security, and click Open Anyway for Switchboard if macOS shows that option.

    Apple only shows this override temporarily and not for every blocked-app dialog. If you do not see it, use the one-line fix above instead.

Why is this needed? Apple Developer ID signing costs $99/year and notarization adds release friction. The beta is unsigned to keep it free and fast to ship. See the FAQ for more.

How Switchboard helps

Built to answer specific questions: which local service owns this process, why is it still alive, what owns this port, and what can I do next?

It finds the things you forgot

Switchboard auto-detects dev servers (port observation), Homebrew services, Docker containers, and launchd jobs — and tags them Discovered so you can tell them apart from services you set up by hand.

A safer stop flow for orphan processes

When Switchboard finds a dev server still listening on a port you forgot about, the detail panel shows a Stop button right there. Confirm, and it sends SIGTERM to the right PID. No lsof, no kill -9 guessing.

One dashboard for every service kind

Running, degraded, stopped, and unknown — the same status vocabulary whether it's Postgres under Homebrew, a dev server on port 5173, a launchd agent, or a Docker container. No tab-switching between four different tools.

Port inspector that names the process

Every listening port, with the actual process and project name attached — not just node 41327. Conflicts are flagged where two things claim the same port.

Live health checks per service

Homebrew, Docker, HTTP, or any command you trust. Switchboard polls each one on its own cadence and shows you the rolling stopped / degraded / unknown breakdown — not a single misleading "100% errors" number.

Logs without three Terminal tabs

Launchd plist StandardOutPath / StandardErrorPath, Docker logs, command output, manual log files, and Switchboard activity — all merged into one live timeline.

Templates for the usual suspects

Postgres, MySQL, MongoDB, Redis, Docker Compose, Ollama, nginx, generic HTTP + command. Every preset's commands are reviewed and approved — no shell magic, no surprises.

Safe by construction

Switchboard never executes a shell string from the UI. Every action maps to an exact allowlisted cmd + args. Destructive ones (delete, force-stop, install from network) require an explicit per-command approval the first time.

Local-only, no account, no telemetry

No cloud. No background HTTP server. No analytics. Your config and logs live under ~/Library/Application Support/. The only outbound request is the daily check for an app update — and that's a Settings toggle away from off.

Why this exists

I kept losing track of the things I'd started.

A dev server here, a database there, a tunnel for some experiment — half of them still running days later, none of them stopped, all of them quietly using CPU and battery I didn't have to spare. macOS doesn't tell you about this. Activity Monitor will list the processes if you go looking, but it won't connect node to the dev server I started last week.

The problem got worse when I started building with AI coding tools — Cursor, Claude Code, Windsurf, Cline, the whole crowd. They're great at spinning up dev servers; they're not always great at stopping the previous one before starting the next. Sometimes the agent is smart enough to free the port it needs — sometimes it just walks to the next available one. After a few hours of iteration you can end up with six copies of the same Vite server competing for memory, the laptop running hot, the battery draining fast, and nothing in macOS surfacing any of it.

You know roughly what you run — you just lose track of what's still running. The fan spins up, the battery drops, and nothing in macOS connects it back to that dev server, worker, or model you started days ago and forgot about.

Switchboard is the thing I wanted: one place where every local service shows up, every forgotten process gets surfaced, and every port flood gets named with its actual cause. The OS won't tell you. The dev tools won't tell you. This will.

What it catches

  • Forgotten services still running days after you stopped paying attention.
  • AI-spawned dev servers your coding agent started and never shut down. Switchboard finds the PID and gives you a clear stop flow.
  • Port-fighting dev servers — multiple copies of the same tool on consecutive ports, competing for resources.
  • Resource spikes macOS doesn't alarm about: heat, fan, battery drain attributed to nothing specific.
  • Orphans that survive sleep, IDE quits, and terminal closes — processes you have no easy way to find again.

Trust model

Switchboard is designed to be useful without becoming a shell-in-a-webview.

  • Runs entirely on your Mac.
  • No cloud account.
  • No background HTTP server.
  • No arbitrary shell from the UI.
  • The webview sends only serviceId, action, and explicit confirmation state.
  • Rust maps actions to exact allowlisted cmd + args definitions.
  • Commands run through tokio::process::Command, never sh -c.
  • Imported commands are previewed command-by-command before they can run.
  • New or changed imported commands stay unapproved until reviewed.
  • Command output is bounded; secret redaction defaults to on.

Frequently asked questions

macOS says the app is "damaged" or "can't be checked" — what do I do?

Both messages are Gatekeeper launch blocks you can hit before Switchboard has Apple Developer ID signing and notarization. Newer macOS releases may show "Switchboard.app is damaged and can't be opened. You should move it to the Trash.". Other systems may show "cannot be opened because Apple cannot check it for malicious software."

The app is not actually damaged. Run the one-line xattr command in the First-time install section to clear the quarantine flag — it works on every supported macOS version. If System Settings shows an Open Anyway override after the first blocked launch, that also works.

Is Switchboard really free? What's the catch?

Yes. The entire beta is free with no license key, no signup, no trial countdown, and no ads. No upsell prompts inside the app.

The stable 1.0 release is planned to be paid. Beta users will be offered either a founder discount or an early-supporter license path before stable pricing starts. Exact pricing has not been announced yet.

Do I need to be a developer to use this?

Switchboard is built first for developer-ish workflows: projects, local databases, dev servers, containers, local AI tools, and ports. You do not need to be a command-line expert, but it helps if you are trying to understand what your machine is running.

You will hit a developer-flavored moment during install (running xattr in Terminal to clear macOS Gatekeeper's quarantine flag — one line, copy-pasted from the install section above). Past that you drive Switchboard from its interface, but getting real value out of it assumes you're comfortable with the services, commands, and ports you run on your machine.

Does it work with Cursor, Claude Code, Windsurf, Cline, …?

Yes — Switchboard is agnostic about what started a process. It watches ports and processes directly, so when your AI coding tool spawns a Vite dev server (or a FastAPI server, or anything else listening locally), Switchboard auto-detects it, tags it Discovered, and gives you a Stop button with confirmation. Doesn't matter which agent or which editor started it.

How is this different from a port manager, or just killing the port?

Switchboard isn't a port pre-assignment tool. Port managers and named-URL routers help an agent pick a free port before it starts a server; killing a port is a one-off. Switchboard gives you the standing, machine-wide picture — what's running, what's draining battery and CPU, what owns each port — plus a safe stop / restart flow, including the long-running local AI tools (Ollama, LM Studio, self-hosted agents) that pile up between sessions. Use them together: coordination decides where things start, Switchboard shows you everything that ends up running.

Do I need an account or license key?

Not during the beta. Download the .dmg, drag Switchboard.app into /Applications, and launch it. There's nothing to sign up for and no license key to enter while the beta is free.

What data does Switchboard collect or send?

None. No telemetry, no analytics, no crash reporter, no background HTTP server. The app does not listen on any network port.

Everything stays on your Mac under ~/Library/Application Support/com.azzuwayed.switchboard/. The only outbound request the app makes is a once-a-day check to the public updates manifest to see whether a newer release is available — and that can be disabled in Settings.

Does it work on Intel Macs?

Not currently. Switchboard ships as Apple Silicon (arm64) only during the beta. An Intel build is not planned before 1.0.

What macOS versions are supported?

macOS 12 (Monterey) or newer, Apple Silicon only.

How do updates work?

The app checks the public updates manifest once a day and shows a non-intrusive banner in the app shell when a new release is available. One click installs the update in place — the new bundle's minisign signature is verified against the public key compiled into the running app before it swaps.

Prefer to install manually? Disable Check for updates automatically in Settings and grab the .dmg from the releases page on your own schedule.

How do I uninstall?

Quit Switchboard from the menu bar, drag Switchboard.app to the Trash, and — if you also want to delete your services configuration — remove ~/Library/Application Support/com.azzuwayed.switchboard/. No system-wide installer to undo.

Is the source available?

The source repository is private during the beta. Whether it goes public has not been decided yet.

Where do I report bugs or request features?

Open an issue on GitHub Issues. Include the build version (Help → About) and a short reproduction when you can.
